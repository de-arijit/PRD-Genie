PRD Genie: AI-Powered Product Documentation Assistant

A 14-day build plan for NeuronForge's documentation assistant — a sequential pipeline that turns messy meeting transcripts into structured PRDs and user stories, without inventing a single requirement that wasn't said out loud.

📅 14 days total runway
🧩 Sequential Pipeline orchestration
🖥️ IK's OpenAI key primary · Ollama (qwen3.5 → mistral) fallback
🤖 4 agents · 3 core + 1 extended
🎯 90 pts across Q1–Q4

Why PRD Genie, and why this shape

Of the four capstone options, only the PRD Genie problem statement and its matching sample data (transcripts, stakeholder notes, product brief, PRD template, baseline eval set) were provided — so the project is already chosen. What's left to decide is the internal design, and the problem statement itself recommends the shape below.

Setup complexity
File uploads only — no OAuth2, no live API credentials. Fastest path to a working v1.
Pattern fit
Every input takes the identical route: transcript → requirements → PRD → stories. That sameness is the textbook signal for a Sequential Pipeline, not a Router.
Richest test data
5 transcripts spanning detailed, vague, contradictory, and empty — built specifically to expose hallucination.
Grounding is explicit
The rubric's core skill — stated vs. assumed — is graded directly by 8 of the 12 baseline tests (T2, T3, T5, T6, T9 especially).

Agent architecture

Design worth 10 of 45 pts on Q3

Four agents, one direction of travel. Each has exactly one job, a fixed input/output contract, and — per the playbook's hallucination guardrail — an explicit instruction for what to do when it doesn't have enough information.

INPUT: transcript.txt / notes.txt / brief.txtOUTPUT: PRD.md + user stories + gap questions
1 · Requirement Extractor
Parses raw text. Separates stated facts from ambiguous/assumed ones. Flags contradictions and missing fields.
→
2 · PRD Generator
Maps extracted fields into prd_template.md structure. Leaves a section blank rather than inventing content.
→
3 · Story Breakdown
Converts PRD features into Epics → User Stories ("As a…") with Must/Should/Nice priority.
→
4 · Gap Analyzer (extended)
Reads the Extractor's ambiguous-item list and produces stakeholder-ready clarification questions.
Hallucination guardrail, in every agent's prompt: "Only use information explicitly stated in the input. If the input is too vague to determine X, say UNKNOWN or list it as an open question — do NOT invent X." This single rule is what T2, T5, and T9 are testing for.
The guardrail has to hold across both tiers of the fallback chain. OpenAI (primary) will generally respect an UNKNOWN rule with less coaxing. qwen3.5:4b (fallback) is far more likely to "helpfully" fill a gap rather than say UNKNOWN — so write the prompt to the fallback tier's weaknesses, not the primary tier's strengths, and re-test T9 on whichever tier actually served the response. Budget for extra guardrail iteration inside Day 4 and Day 11.

14-day plan, in 6 phases

Compressed from a real 10–12 week agentic AI engagement shape

A real forward-deployed engagement runs Discovery → Setup → Baseline → an iteration Loop (where most of the value sits) → Hardening/Handover, typically over 10–12 weeks with a 4–5 person pod. This plan compresses the same six phases into 14 solo days — the proportions carry over even though the absolute time doesn't: the Loop still gets the largest share of build time, and every phase ends with a named artifact a TPM would actually leave behind, not just a checklist.

Playbook's #1 failure mode: building all 4 agents before testing any of them. This plan tests each agent independently before wiring the next one in.

Day 11 — Evaluate and iterate

Run correctness AND token-optimization cycles, both documented

  • Inspect traces for T9 and T2 specifically — these are where models most often slip and invent content, and where the fallback tier is weakest (see Tool Stack note above).
  • Copy cycle-template.md for this cycle. Fill all 5 stages as you go, not retroactively — Learn and Change are much harder to reconstruct from memory afterward. Mark each cycle's type: Correctness, Token optimization, or Both.
  • Correctness cycle: identify which agent produced the failure, add a guardrail line to that agent's prompt. Re-score: re-run the same input, then the full 12 to check for regressions.
  • Token-optimization cycle: check the dashboard's Token Usage panel — target whichever agent shows the largest positive variance (PRD Generator is the likely first target — see ground-rules.md → "Where to optimize"). Change the prompt/template handling to reduce tokens, then re-score BOTH token count and correctness — a shorter prompt that also drops the UNKNOWN guardrail is a regression, not a win.
  • POST the cycle's summary to /cycles so it shows up in the dashboard's cycle log automatically on next refresh.
  • Aim for at least 2 full cycles by end of day — a correctness cycle and a token-optimization cycle, so the writeup can show both loops in action, not just one.

Live evaluation system

Beyond baseline — Q3 depth + Q4 evidence

The playbook's Step 6 loop — Run → Score → Learn → Change → Re-score — is usually done ad hoc and half-remembered by submission day. This project makes it a small piece of real infrastructure instead: every cycle is scored against a written ground-truth spec, logged automatically, and visible as a dashboard that updates itself.

SOURCE: n8n pipeline runsDESTINATION: dashboard.html, refreshed
n8n pipeline
After each test case, an HTTP Request node POSTs the result to the eval service.
→
Eval service FastAPI + SQLite
Scores against ground-rules.md, stores per-test/per-agent results (incl. tokens on every tier), computes estimate-vs-actual, exposes /summary.
→
Cloudflare Tunnel
Exposes the local service so it's reachable outside your machine.
→
Scheduled task
Every 30 min: pulls /summary, regenerates dashboard.html, delivers the updated file.
Ground rules
ground-rules.md — the 12 baseline tests expanded into explicit pass/fail criteria, plus a Gap Analysis rubric. This is the "ground truth" every cycle scores against.
Cycle documentation
cycle-template.md — one filled copy per Run→Score→Learn→Change→Re-score iteration. Feeds the dashboard's cycle log and the Q3/Q4 writeup directly.
Two metric tiers
Technical (hallucination rate, extraction completeness, format compliance, fallback rate, latency) answers "does it work." Business (time saved, cost/PRD, draft-readiness, requirement-loss prevented) answers "is it worth it."
Token estimate vs. actual
Per-agent token targets set Day 2 (see ground-rules.md), logged live from every call on every tier, compared and ranked by variance — the dashboard's "optimize this next" list, not just a cost figure after the fact.
Delivery
A regenerated dashboard.html file, not a hosted page — works with or without a persistent public URL, and ships cleanly inside the GitHub repo.
OpenTelemetry — documented, not built. Given the 14-day clock, this project stays on Langfuse's native SDK rather than standing up a full OTel Collector. Langfuse is itself OTel-compatible: the documented upgrade path is n8n emitting spans via an OTel SDK → a local OTel Collector → OTLP export into Langfuse (or any OTel backend), which would decouple instrumentation from the trace-viewer choice entirely. Write this up explicitly in the Q3 design section as a considered tradeoff, not an omission — it demonstrates the same architectural judgment without spending a build day on it.

Where hallucination is most likely to hit

High

T9 — empty transcript

"Meeting happened. Notes: none." Weakly-prompted models will still produce a generic PRD because that's the "helpful" default. The Extractor's UNKNOWN rule has to override the model's instinct to be useful.

High

T2 — vague AI request

"Something like what Competitor X has" invites the model to invent plausible-sounding features. Must produce a question list, not a spec.

Medium

T3 — contradictory requirements

5-second refresh vs. minimize API calls. Models tend to silently resolve conflicts in favor of whichever was stated last. Must surface the tension instead.

Medium

T7 — exact technical numbers

10,000 users / 200ms p95 / Salesforce v52. Generation steps sometimes round or paraphrase numbers when restructuring into NFR format.

Medium

Chained hallucination (T11→T12)

An invented detail in the PRD Generator's output silently becomes a "requirement" by the time Story Breakdown runs. Trace both steps together, not just individually.

Medium

Template drift

PRD Generator gradually reordering or renaming prd_template.md sections across different inputs — breaks the "format compliance" production metric.
